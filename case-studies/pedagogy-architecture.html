The pedagogy that lives where the model isn't

The platform case study describes the teaching context, work with approximately 20 students over more than one year, and priorities for evaluation.

01 — What this system is

Three surfaces around one live hour

A single teacher teaches Russian-speaking expats in Spain, one-on-one, online. This system is everything around that live hour:

a lesson player the teacher drives on screen during the hour; a homework runner the student does alone, between lessons; and a teacher console that assigns work, reviews student work and machine feedback, and shows where students fail.

These notes focus on the data-driven lesson structure: JavaScript objects organized around a shared schema and a runtime registry. The platform also includes teacher-facing tools for creating and editing lessons and activities, managing sequences, and assigning work.

The single most consequential decision sits at the top, and it is a decision not to use AI. The lesson template states it directly — "the AI conversation partner is not used in the lesson; the live partner is the teacher." LessonPage renders only deterministic engines — flashcards, drills, dialogues, a mission graph — and never opens a chat to a model. This is a product decision as much as a pedagogical one: the student is paying for an hour of a human, and the AI's job is not to imitate that human in the room. Its job is to extend the teacher's reach into the homework the teacher cannot sit through. Everything below follows from that boundary.

02 — Where the LLM is, and where it is gated out

A wall of deterministic code in front of every model call

The system has exactly one server-side LLM seam — a PHP endpoint, check.php, reached through src/utils/api.js — plus a Cloudflare Worker proxying DeepSeek for chat. The interesting design is not where the model is called. It is the wall of deterministic code in front of every call.

Grading runs as a cascade. checkSingleTask settles every closed question by comparison, settles spelling by rule, and reaches the model only for free text that survived both: 

// 1 · exact match, punctuation- and case-insensitive
if (strictUser === cleanTextStrict(cand)) return { status: 'correct' };

// 2 · accent-insensitive match → a rule decides spelling vs. correct (see 03b)
if (cleanTextNoAccents(userAnswer) === cleanTextNoAccents(cand)) { /* ... */ }

// 3 · only now, for fill_gap / translation, ask the model
return await checkTranslationWithAI(userAnswer, task.correct, task.context);

The consequence is that matching, multiple_choice, true_false, who_said and reading-comprehension questions never reach a model at all, and the common case — a correct answer — costs zero tokens and survives an outage.

03 — Three decisions that are pedagogy and engineering at once

Each begins as a question a teacher would ask, and ends as a line of code

03a — Forgiving practice, strict tests

The question. When the grader is unsure — a network blip, a malformed model response — should the student get the benefit of the doubt?

The answer, in code. It depends on the stakes, and the code says so in two catch blocks. Homework grading fails open: when a call to the grader throws, the student's answer is accepted — the comment in the code reads "so as not to punish the student for our failure." The placement test fails closed: the same shape of catch, the opposite return value, so any gap the local check and the model both leave unknown becomes an error, not a free pass.

This difference raises a pedagogical trade-off between continuity and assessment validity. Accepting an answer during a service failure lets practice continue, but can give misleading feedback. Rejecting an answer avoids awarding credit without a judgment, but can penalize a learner for a technical problem. I would make an unavailable judgment explicit and flag it for review in both contexts.

03b — Grading accents by what they mean, not by string distance

The question. A student writes hable for hablé, or cafe for café. Same number of characters wrong. Are they the same mistake?

The answer, in code. No — and the system encodes why not in a model but in a table of Spanish homographs and one suffix rule: 

const TILDE_HOMOGRAPHS = new Set([
  'sí','tú','él','mí','té','sé','dé','más','aún',
  'qué','cómo','dónde','cuándo','cuál','quién', /* … */
]);

const tildeIsCritical = (c) => {
  if (TILDE_HOMOGRAPHS.has(c)) return true;
  if (/[éíó]$/.test(c) && c.length >= 3) return true;  // hablé, comió, viví
  return false;
};

café and también lose nothing; their accent is orthographic. hablé versus hable — preterite versus subjunctive — costs half credit, because dropping the accent changed the grammar. This is error gravity: feedback weight tracks communicative cost, not orthographic perfection. There is no separate "pedagogy layer" deciding the tilde matters; the homograph set is the pedagogy, and it runs before any model is consulted.

03c — The machine grade is provisional; the teacher is the arbiter

The question. Who has the last word on a grade — the machine, or the human?

The answer, in code. The human, structurally. The console lets the teacher overturn any machine verdict, and the data model is built to expect it. The machine's verdict is never discarded — it is preserved as originalStatus while the displayed grade flips and the score recomputes. The level-skip path does the same at coarser grain: the teacher convalidates a whole CEFR level while preserving every real attempt.

This closes a loop with 03a. Fail-open grading — accepting on doubt — is only defensible because this human backstop exists. The model is allowed to be lenient and occasionally wrong precisely because it is not the final authority; a teacher reviews and corrects, and the code carries the seam (originalStatus) that keeps the original judgment available for comparison. This makes teacher review part of the assessment workflow.

04 — Decisions encoded structurally

Some decisions live in the shape of the data, not in a function

Tab order is an acquisition sequence. LessonPage renders a fixed array of tabs — diagnostic → recognition → controlled practice → spaced retrieval → bridge to production → communicative → transfer → exit ticket — regardless of the order the author wrote them. The author cannot accidentally put free production before recognition; the gradient from maximum support to minimum is enforced by render order, not by discipline.

conceptId is the spine. Lessons declare what they introduce and what they prerequisite; a runtime index builds a Map<conceptId, items[]> across every lesson, and the warm-up pulls retrieval items from prerequisite concepts taught in earlier lessons. Interleaving across lessons is a property of the data graph, not of any one lesson.

Authoring for a target-language environment. The authoring conventions call for hidden translations and limited use of Russian in designated support slots. These are content-design guidelines; automated enforcement is an improvement to explore.

05 — Three tiers of evidence

Distinguishing participation, performance, and transfer

01 — Engagement

Did the student do the work? — Recorded.

Per-tab progress and submission completion land in Firestore. This is the best-instrumented tier, and it measures attention, not learning: for passive tabs the only signal is that the tab was opened.

02 — Performance

Can the student do the task now? — Partly recorded.

Submission scores and the console's error analytics are real: every submission aggregates into error-rate-per-task and average-score-per-homework. The exit ticket re-runs the diagnostic items and shows a delta — but it re-runs the same items (so it is Performance, not Transfer), and it lives in localStorage, visible to the student only; the console never sees it.

03 — Transfer

Can the student do it somewhere else? — Designed for, not measured.

The conceptId spine is precisely a transfer scaffold — the same concept is required to resurface in a later lesson's warm-up, in a different engine, with different lexicon. But warm-up performance is not recorded, and nothing aggregates whether a concept introduced in lesson N is still retrievable in lesson N+3. The architecture is shaped for transfer; evaluating it would require new tasks and later follow-up.

06 — Design trade-offs & next steps

Improve scheduling, authoring clarity, and feedback

Lesson warm-ups need a spacing schedule.

The warm-up mixes prerequisite concepts through seeded random sampling, without using time intervals or the student's error history. The documented vocabulary design uses a Leitner review approach; extending scheduled review to lesson warm-ups is a separate next step.

Next move: a per-concept lastSeen timestamp, and a scheduler that picks warm-up items by interval rather than by sampling.

Authoring guidance needs a clearer boundary.

The chat-scenario template combines fields that control the activity with fields used only as planning guidance. This can make authoring confusing: changing a planning field does not change the learner experience.

Next move: connect relevant fields to prompt assembly and move planning-only guidance into clearly labeled authoring documentation.

The grader has no constraint layer, and fail-open can teach the wrong thing.

The voice tutor notes propose a response checklist. A similar validation step would help the homework grader, which accepts answers when the grading service fails. Teacher review provides a way to correct these judgments, but a learner may encounter misleading feedback before that review takes place.

Next move: a confidence/constraint layer that flags low-confidence and fail-open grades for review instead of passing them through as correct.

The throughline: in the parts of this system where there is no model, there is no separate pedagogy layer either. The acquisition sequence is the tab array. The error-gravity policy is a homograph set. The formative/summative line is two catch blocks. The decisions were made once, and they are visible from both sides.
